# 저장 이전과 구매 복구 위험 검토

2026-10-16 / P1-003 정적 검토 후 P1-007 설계 보완. 사용자 승인 범위는 **P1-003부터 검토하는 순서**이며 아래 이전 기본값·환생·기능 접근 정책이나 기술 설계를 일괄 승인한 것이 아니다. 게임 코드·실제 저장·서버 지갑은 변경하지 않았다. 앱/서버 테스트·SQLite 이전·실패 주입·실기기 검수는 **미실행**이다.

## 3. 이전 파이프라인 제안

1. 저장 작업을 직렬화하고 지원하는 구형 형식/정합성부터 검사한다. 손상 원본을 새 기본값으로 조용히 대체하지 않는다.
2. 원본 current·backup과 이전 출처/계정 식별을 보존하는 별도 복구 사본을 준비한다. 일반 current/backup은 다음 save로 교체되므로 장기 원본 보관 대체물이 아니다. 보관 방식/기간은 기술·정책 결정 대기다.
3. 메모리에서 후보 새 상태를 만들고 자산별 보존 비교표를 작성한다. 문자열 BigInt·정수배율·기존 원장·상품/권리 ID를 유지한다. 알 수 없는 데이터는 삭제/무료 지급하지 않고 복구 필요로 분리한다.
4. 같은 이전 작업 ID/출처 해시와 고정 전환 기준을 사용한다. 재시도마다 새 초기 보상·새 부재 정산 구간을 만들지 않는다.
5. 데이터와 이전 완료 표식은 한 로컬 트랜잭션으로 저장하는 안을 검토한다. 실제 포맷 변경과 롤백 지원 범위는 구현 전 결정한다.
6. 저장한 current를 다시 읽어 포맷·순번·완료 표식·보존 자산을 검증한다. stale save가 무시된 경우에도 성공으로 안내하지 않는다. 재읽기 실패면 보존 원본에서 복구하는 경로로 연결한다.
7. 서버 황금·권리·미완료 거래를 대조한 뒤 새 지출/환생을 연다. 이전 과정에서 서버 지갑을 로컬 캐시로 덮어쓰지 않는다.

다운그레이드 앱이 새 포맷을 읽지 못할 수 있다. 구형 앱으로 원본을 강제로 덮어쓰는 방식은 복구 전략으로 확정하지 않으며, 구형 클라이언트 차단/원본 복귀 시 서버 거래와의 정합성까지 검토해야 한다.

## 4. 구매 전 백업과 분산 결제 복구

일반 스냅샷과 별도로 거래 ID·계정·로컬 차감/지급·서버 영수증·적용 기준을 보호하는 기록을 제안한다. **같은 SQLite에 있다고 백업/앱 삭제까지 자동 보호되는 것은 아니다.** 백업 교체는 해당 기록을 되돌리지 않도록 구현해야 하며 전체 데이터 삭제/재설치에는 로컬 증거가 사라질 수 있다.

| 발견 상태 | 제안 처리 | 금지할 단정 |
| --- | --- | --- |
| 로컬 차감 완료, 서버 결과 불명 | 같은 ID의 서버 결과 조회 후 기존 거래 복구 | 타임아웃=취소, 즉시 환불 |
| 서버 committed, 로컬 지급 미완료 | 같은 영수증으로 상품/효과를 최대1회 적용 | 새 requestId로 재구매·서버 잔액을 과거 값으로 복원 |
| 서버 canceled 최종 확정 | 로컬 차감/예약을 같은 ID로 한 번 보상 | 취소/확정이 동시에 가능한 비내구 상태 처리 |
| 구매 전 backup + 보호 기록 존재 | 스냅샷과 미정산 거래를 대조해 필요한 차감/지급을 각각 확인 | 스냅샷 순번이 높다는 이유로 복구 완료 |
| 재설치·다른 기기 + 로컬 차감 증거 없음 | 검증할 수 없는 부분을 보류하고 지원/복구 경로 제시. 영구 권리는 기존 서버 기록과 별도 검토 | 황금 차감 영수증만으로 로컬 재화 차감 여부까지 증명하거나 임의 재차감/무료 지급 |
| 소비성 boost·반복 스킬 거래 | 기존 fresh-save 소비성 제외와 회차별 grant 식별을 구분 | 모든 서버 grant 무조건 재생 |
| 계정 전환 중 pending | 계정별 거래를 분리하고 기존 계정의 결과를 먼저 대조하는 안 검토 | 다른 계정 지갑에 차감/상품/대기 광고를 옮겨 지급 |

일반 영구 권리 복원과 **새 복합 결제의 로컬 비용 복구**는 별개다. 새 복합 구매·환생·백업 복원을 열기 전 조정이 필요한 거래를 확인한다. 불명 거래 때문에 일반 오프라인 플레이 전체를 막는 범위는 최소화하되 공유 재화 안전성이 깨지는 명령은 제한한다. 구체 지원 경로·보관 기간·기기 간 진행 권위는 미정이다.

## 5. 광고 타이머 확정과 정산 분리

광고 시청 중 손님 대기·큰 틀 제작·6구 익힘을 정지하고 복귀 시 같은 진행에서 재개하며 광고 시간을 소급 반영하지 않는 정책은 이번 사용자 승인이다. 영업 상태와 붕어빵력 생산/정산, 광고 일일키·예약 만료·서버 검증 시각은 멈추지 않는다. 경제 구간을 이미 처리했다면 같은 광고 시간을 resume/offline 구간으로 다시 지급하지 않도록 한 정산 cursor로 연결한다.

구현 제안은 광고 시도 ID에 연결된 시작/정지 구간과 정지 사유를 내구 기록하고, 광고/전화/앱 이탈이 겹쳐도 정지 해제가 중복되지 않게 하는 것이다. 승인 범위는 광고 구간이며 강제 종료로 광고 종료 시각을 알 수 없는 경우의 영속 세션 처리까지 확정한 것은 아니다. 해당 불명 구간을 영원한 무료 정지나 전체 일반 백그라운드 정지로 확대하지 않는다. 검증 가능한 경계·세션 복구의 기대값을 정한 후 구현·실기기로 확인한다.
