### 1.2. 발견한 불일치와 처리

- 공통 기준·상세·이전 문서의 ‘팥 기본’만으로는 **팥 미디엄 레시피 기본 지급**을 구별할 수 없었다. 최신 확정으로 명확히 한다.
- 숙련5종 조건·실패 연습 인정·주문 제작 반영이 계속 미정으로 적혀 있었다. 이미 답변한 범위는 확정으로 갱신한다. 정확 횟수·손기술 판정·굽기 경계는 계속 미정이다.
- ‘초기 황금 0 때문에 시작 레시피를 못 산다’는 질문은 최신 답변으로 전제가 없어졌다. 초기 핵심 진행은 구매 없이 가능하며 재질문하지 않는다. 이후 유상 스킬 가격과 첫 황금 획득 보장은 별도 미정이다.
- 덜 익음을 무조건 판매 불가 또는 손기술 실패로 취급하는 추천을 확정으로 쓰지 않는다. **특별 주문의 요구 충족**과 별점/황금 자격을 분리한다.
- `_applyGrant`가 중복 권리 지급을 막는다고 해서 두 재화의 분산 차감이 이미 구현됐다고 볼 수 없다. 현재 spendGold의 요청 ID는 호출마다 새로 만들어져 복합 구매의 지속 의도 ID를 대신하지 못한다.

## 2. P1-002 — 레시피·숙련·판매·해금·가격 계약

### 2.1. 이미 확정된 플레이 계약

1. 신규 시작 시 **팥 미디엄 레시피만** 기본 지급한다. 시작 레시피를 사기 위한 황금은 필요하지 않으며 구매 없이 핵심 플레이를 진행한다. 기본 레시피 지급을 초기 숙련/6구/도감 전체 완성으로 확대하지 않는다.
2. 다른 맛 자체는 상점 OR 지정 미션으로 간헐 획득한다. 해당 맛으로 다른 익힘 결과를 직접 만들어 익힘별 레시피를 수집하며, 시도할 익힘 레시피의 선구매/보유를 요구하지 않는다. 다른 맛의 최초 진입 익힘은 미정이다.
3. 숙련은 **맛별**이다. 연습에서 익힘5종 수집 AND 인정 연습량 충족 AND 손기술 통과량 충족을 모두 요구한다. 전체 수집 기록과 **연습에서 얻은 수집 기록**을 분리한다.
4. 끝까지 꺼내 저장 확정한 실패 연습도 연습량에 포함한다. 주문 제작은 익힘 수집만 인정하고 연습량·손기술에는 합산하지 않는다. 취소·미완료는 수집/연습을 생성하지 않는다.
5. 동일 결과 ID의 수집·연습·숙련·도감 완성·6구 해금은 한 번만 저장한다. 저장 실패는 같은 판정·결과로 재시도한다. 팥도 숙련한 뒤 6구 후보가 된다.
6. 덜 익음은 특별 주문에서 판매할 수 있다. 일반 주문 자격으로 확대하지 않는다. 취합 답변의 가운데3종 일반 판매·타버림 판매 불가 범위를 유지하되, 미디엄의 단계 대응과 최종 5명칭·시간 경계는 미정이다.
7. 보유 레시피의 큰 틀 연습/즉석 판매를 추가 레벨·누적 획득 조건으로 재잠금하지 않는다. 도감·친구 등 기능 UI 해금과 생산 자격을 혼동하지 않는다.

## 3. P1-007 — 복합 결제·판매 보상 복구 설계안

### 3.1. 권위와 안전성의 한계

서버 황금과 로컬 SQLite 붕어빵력은 다른 저장소다. 단일 원자 트랜잭션이나 ‘실패 시 언제나 즉시 환불’을 약속하지 않는다. 서버는 황금·예약·결제 영수증·지급 결과의 권위, 로컬은 현재 붕어빵력·클리커·진행의 원본이다. 로컬 차감 완료 보고만으로 로컬 재화의 변조 방지까지 서버가 보장할 수 없다. 전면 서버 경제 이전은 미확정이다.

다음은 기존 지갑을 재사용하는 **작성자 기술 제안**이다. 실제 엔드포인트·DB 필드명·예약 유효시간을 확정하지 않는다. 온라인에서만 복합 구매한다는 정책은 이번 사용자 답변으로 확정이다. 일반 오프라인 플레이는 유지하고 중단된 기존 결제는 같은 ID로 복구한다. 오프라인 신규 구매 신청·선지급은 도입하지 않는다.

### 3.2. 거래 식별과 최소 증거

지속 거래 ID는 네트워크 호출 전에 저장하고 계정에 묶는다. 견적에는 상품/스킬 ID·가격 버전·구매 시작 회차·수량·두 비용·기능 조건을 고정한다. 같은 ID로 다른 payload가 오면 충돌로 거절한다. 재시도/다른 기기/앱 재시작 때 새 ID로 바꾸지 않는다. 유상 연속 스킬과 소비성 상품은 기존 영구 소유 entitlement 규칙을 그대로 복사할 수 없으므로 거래/회차로 중복을 판정한다.

로컬 거래 기록에는 예약·붕어빵력 차감 여부·서버 영수증·상품 적용 여부·적용 저장 순번을 둔다. 서버는 승인 견적·황금 예약·최종 committed/canceled 결과·grant를 남긴다. 잔액은 BigInt/10진 문자열 원칙과 기존 gold 저장의 수치 범위를 구분하며, 서버 입력의 음수·범위 초과·가격 불일치를 검증한다.

### 3.3. 상태 전이 제안

| 단계 | 내구 기록과 허용 전이 | 종료·응답 유실 때 |
| --- | --- | --- |
| 의도 저장 | 로컬 두 비용 가용성·해금 확인, 붕어빵력 예약과 의도 저장. 최종 차감/상품 지급 없음 | 실패면 서버 요청하지 않음. 예약분은 다른 구매에 재사용 금지 |
| 서버 준비 | 서버 견적/계정/회차 검증 및 황금 예약. 부족·가격 변경은 거절 | 결과 조회로 예약 유무 확인. 자동 가격 변경·재구매 금지 |
| 로컬 차감 | 붕어빵력 차감과 debit-applied를 같은 SQLite 저장으로 확정 | 저장 실패면 최종 서버 소비 요청하지 않고 취소 결과 확인 |
| 서버 확정 | 예약을 소비하고 거래 committed·영수증·grant를 같은 서버 트랜잭션에 기록 | 타임아웃은 결과 불명. 같은 ID 조회/확정 재시도; 즉시 로컬 환불 금지 |
| 로컬 상품 적용 | 영수증 검증 후 의도/차감/상품 적용을 한 저장으로 확정 | 적용 실패는 같은 grant 재적용. 추가 차감·다른 상품 지급 금지 |
| 취소·보상 | 서버가 canceled를 최종 확정한 경우에만 로컬 차감/예약을 같은 ID로 한 번 복구 | 늦은 확정과 취소는 서버에서 직렬 판정. committed는 취소 환불 경로로 바꾸지 않음 |

가격 변경은 기존 견적의 처리 결과를 먼저 결정한 뒤 새 견적을 명시적으로 제시한다. 수량·가격 동의 없이 낮은 등급이나 작은 수량을 대신 구매하지 않는다. 부족 시 최종적으로 어느 재화도 소비하지 않는 계약을 유지하되, 중간 대기 상태와 예약 잔액은 사용자에게 표시한다.

### 3.4. 백업·계정 변경·소비성 상품의 미해결 위험

현재 current/backup은 다음 저장으로 교체되는 스냅샷이므로 거래 기록까지 과거로 돌아갈 수 있다. 구매 전 백업에서 grant만 다시 적용하면 로컬 붕어빵력이 복제될 수 있다. **제안:** 일반 스냅샷 복원으로 되돌리지 않는 거래 보호 기록과 서버 영수증의 단조 기준을 대조하고 미정산 거래가 있으면 해당 구매·환생·백업 교체를 복구 전 제한한다. 보호 기록까지 소실되거나 두 기기 로컬 진행을 연결할 근거가 없으면 자동 환불/재차감/무료 지급하지 말고 복구 필요로 보류한다.

서버 계정과 로컬 진행의 연결, 구형 구매·재설치·소비성 boost를 다시 적용할지의 규칙은 P1-003/DEC-010 선행이다. 영구 구매 grant 전부 재생을 소비성·반복 구매에 적용하지 않는다. 복구 불가능한 경우의 지원 경로·보호 기록 보관 기간도 미정이다. 이 한계가 해결되기 전 이 설계를 구현 착수 가능·분산 결제 완료라고 표시하지 않는다.

### 3.5. 판매 희귀 보상

판매 ID에 주문·실제 소비 제품·신선도·명시 요구 충족·별점 근거·판정 버전을 연결한다. 로컬 판매 완료·일반 대금·제품 소비·황금 심사 대기를 원자 저장한다. 서버는 검증 가능한 판매에 대해서만 한 번 추첨하고 **미당첨도 저장**한다. 당첨·grant·지갑 증가를 함께 확정한다. 검증 불가 판매는 미당첨으로 위장하지 않고 보류/거절 사유를 구분한다.

서버에 클라이언트 별점만 제출하는 것은 증명이 아니다. 서버 발급 주문/허용 제작 근거·증거 보관·재사용 금지·오프라인 검증 가능 범위는 구현 전 게이트다. 오프라인 판매도 심사 대기하고 연결 후 서버 검증·1회 추첨한다는 정책은 이번 답변으로 확정이다. 검증 불가 시 지급을 보장하지 않으며, 오프라인 중 새 판매 자동 생성이나 황금 선지급을 허용하지 않는다.

## 4. P1-008 — 선택형 보상 광고 설계안

### 4.1. 확정 범위와 미정 게이트

선택형 보상 시청으로 하루 최대2회 황금을 얻는 것만 확정이다. 강제 전면/배너·일반 분석/추적 허용으로 확대하지 않는다. 획득 UI 위치·해금·업체·SDK·보상량·데이터/동의 및 정지 중 앱 이탈 복구는 미정이다. 광고 세 타이머 정지는 사용자 승인으로 확정이다. 로그인 계정별·KST 자정·서버 시작 승인일 귀속은 이번 답변으로 확정이다. `no_tracking_sdk_test.dart`·개인정보처리방침·Play 데이터 보안은 현재 무광고 구현을 설명하므로 지금 광고 사용 사실로 바꾸지 않는다.

### 4.2. 서버 한도·지급 상태 전이 제안

1. 서버가 사용자 자격·일일키·잔여 슬롯을 확인하고 광고 시도 ID·슬롯 예약·업체 검증에 묶일 불투명 토큰을 발급한다. 슬롯 예약과 한도 검사는 같은 트랜잭션에서 수행한다.
2. 사용자가 명시적으로 시작한 광고만 재생한다. 클라이언트 광고 닫힘/보상 콜백은 대기 UI의 힌트이지 서버 지갑 지급 근거가 아니다.
3. 선정 업체의 검증 가능한 보상 증거를 서버에서 검증한다. 서명·발급자·앱/광고단위·계정/시도 토큰·거래 ID의 재사용·시간 조건을 확인하는 설계이며, 업체 기능 지원 여부는 선정 후 확인한다.
4. 유효 보상 결과는 슬롯 consumed·업체 거래 중복 방지·server grant·황금 잔액을 같은 서버 트랜잭션에 반영한다. 같은 콜백/다른 기기 재시도는 동일 결과를 반환한다. 지급량은 승인된 보상 버전에 묶으며 미정이면 실제 시청을 열지 않는다.
5. 서버 성공 후 로컬 저장 실패는 sync로 같은 grant를 복구한다. pending 황금은 표시할 수 있지만 확정 잔액이나 구매 가능액에 포함하지 않는다.

### 4.3. 만료·실패·자정과 시간

불명확한 보상 결과를 실패로 단정해 예약을 즉시 해제하면 늦은 서버 콜백과 새 시도로 3회 지급이 가능해진다. 예약 만료·시도 최종 종료·늦은 콜백의 수락 가능성을 서버에서 함께 직렬 판정해야 한다. 최종 거절 시도는 이후 콜백으로 성공 전환하지 않으며, 사용자에게 완료 시청으로 안내한 건을 임의 만료시키지 않는다. 검증 지연 허용·재검증·예약 유효시간은 업체 확인 후 결정한다. 미해소 예약은 한도에 포함한 채 복구 안내한다.

**사용자 확정:** 로그인 계정별 한도·KST 자정·서버 시작 승인일 귀속. 여러 기기가 같은 두 슬롯을 공유하고 자정 뒤 도착한 검증도 원래 시작일에 반영한다. 기기 시계·재설치·영업 시작/종료·환생으로 일일키를 초기화하지 않는다. 기기별 별도 한도나 검증 도착일로의 임의 이동은 적용하지 않는다.

광고 중 손님·큰 틀·6구의 세 타이머 정지는 사용자 승인으로 확정됐다. 겹친 앱 이탈/강제 종료의 실제 세션 복구는 별도 기술 검토다. ‘영업 중 앱 종료에도 영업 유지’와 ‘광고 중 손님 타이머 정지’는 같은 결정이 아니다. 보상 시청으로 자동 제품 수확·재고·숙련을 지급하지 않는다. 광고 중 오디오/센서는 플랫폼 동작 확인이 필요하며 실기기 확인 전 동작 성공을 단정하지 않는다.

### 4.4. SDK·정책 검토 체크

- 후보 SDK의 보상 서버 검증 지원·Android/Flutter 버전 호환·동의/미성년자 처리·권한·광고 ID·설치/기기 ID·제3자 전송·필수 수집·보관·삭제를 비교한다. 업체가 선택되지 않아 이번에 실제 수집 항목을 채우지 않는다.
- SDK 추가 전 기존 금지 목록을 보존하고 승인할 SDK/필수 항목만 좁게 검토한다. 금지 테스트를 삭제하거나 전체 허용으로 바꾸지 않는다.
- 실제 SDK/동작에 맞춰 개인정보처리방침·Play 데이터 보안·스토어 광고 신고·README·MASTER·검수를 함께 갱신한다. 현재 광고 없음 문구와 미래 예외를 분리한다.

## 7. 문서 검토 결과와 완료 범위

P1-001은 원래 완료 조건인 현재 코드·최신 확정·미정·출시 범위의 **정적 대조 작업**이다. 09번 검수 기준도 선행 조사에 전체 플레이 검수 통과를 요구하지 않는다고 명시한다. 이번 대조와 문서·원장 검증을 마치면 조사 작업만 완료할 수 있으며 게임 기능/연결 AC 완료를 뜻하지 않는다. P1-002는 가격·횟수·성장/기능 표, P1-007은 P1-003과 복구/판매 증거, P1-008은 P1-007·SDK/보상/정지 구현과 세션 복구 검수가 남아 완료할 수 없다.

## 8. 광고 중 게임 시간 — 사용자 승인 반영

관련 DEC-006/017/026, P1-008, AC-REQ07-902. 광고는 사용자가 선택하지만 그동안 조작할 수 없으므로 손님 시간 초과·제품 익힘을 어떻게 처리할지 별도 결정이 필요하다.

- **사용자 확정:** 광고 중 손님 대기·큰 틀 제작·6구 익힘 타이머만 일시정지하고 복귀 시 같은 진행부터 재개한다. 광고 시간을 이 세 타이머에 소급 반영하지 않는다.
- **미채택 대안:** 실제 경과시간대로 계속 진행해 손님 시간 초과·제품 타버림이 가능하도록 한다. 제품은 여전히 직접 수확만 재고 반영한다.

두 안 모두 영업 상태를 임의 종료하지 않고 붕어빵력 생산/정산은 별도 기존 계약을 유지한다. 정지안도 광고로 자동 제품/숙련을 지급하거나 일반 제작 중 손님 시간까지 정지하는 승인이 아니다. 앱 이탈 전체의 세션 정책·광고 검증 지연·강제 종료 복구는 별도 기술 검토다. 사용자의 “세 가지 추천대로 진행”으로 첫 안을 승인했다.

## 9. P1-003 검토 후 보완

[13번](13_저장이전과구매복구위험검토.md)에 stale save 무반영·구매 전 backup·로컬 증거 없는 재설치·소비성 권리·구형 레벨 제한·첫 부재 정산 위험과 복구 매트릭스를 추가했다. 보호 기록은 제안이며 데이터 삭제까지 보존된다고 단정하지 않는다. [14번](14_밸런스조정용미승인초안.md)에 수치 비교 후보를 분리했다. P1-003은 이제 정적 검토에 착수했으나 실제 위험 검증은 미완료이며, P1-007/008의 선행 충족이나 출시 수치 확정으로 처리하지 않는다.
