## 2. 구매 저널의 처리와 제한

`PurchaseJournal.start`는 양의 두 비용과 계정·거래 ID·스킬·가격 버전·회차·수량을 고정한다. `recordReservation`은 같은 견적의 reserved 응답, `recordDebit`은 예약 근거, `recordServerResult`는 같은 견적의 committed/canceled 응답을 요구한다. 최종 서버 영수증 ID를 보존하며 committed는 지급 ID도 보존한다. 같은 거래의 영수증/지급 ID 변경은 충돌로 거부한다. 실제 서버 인증은 backend 어댑터의 책임이며 필드 비교로 대체하지 않는다.

- 서버 결과 불명에는 최종 결과 메서드를 호출하지 않고 같은 거래를 조회한다.
- committed와 로컬 차감 증거가 모두 있어야 상품 적용을 기록한다. 차감 증거가 없으면 서버 결과는 보존하지만 자동 지급/재차감을 막는다.
- canceled와 로컬 차감 근거가 모두 있어야 복원을 기록한다. 복원 완료의 같은 호출은 같은 상태를 돌려주고 다시 환불하지 않는다.
- 서로 다른 최종 서버 결과, 취소 뒤 지급, 확정 뒤 환불, 예약 없는 차감은 거부한다.
- 계정별 미정산 조회로 재시작 시 지속 거래 ID를 찾을 수 있다. 다른 계정의 거래는 조회 결과에 섞지 않는다.
- 가용액 계산은 동일 로컬 지갑의 예약분만 제외한다. 같은 계정이라는 이유만으로 다른 기기의 붕어빵력과 저널을 합치면 안 된다.

**중요한 연결 조건:** recordDebit/Application/Restoration은 재화·상품을 실제로 바꾸는 명령이 아니다. 같은 SQLite 트랜잭션에서 스냅샷의 실제 차감/상품/복원과 저널을 함께 저장해야 한다. journal-only save를 경제 변경 완료로 취급하지 않는다.

저장소는 expectedSequence와 실제 순번을 비교하고 한 번의 허용 전이만 저장한다. 오래된 상태·견적 교체·전이 건너뛰기는 JournalConflict이며 최신 기록을 다시 읽어 대조한다. 저널만 초기화하거나 오래된 GameState backup과 무조건 조합하지 않는다.

SQLite 저장소는 외부 Database를 받아 initialize 호출 시 development_purchase_journal_v1 테이블만 준비한다. 앱 시작/DB 버전/기존 스냅샷에는 자동 연결하지 않았다. writeInTransaction은 같은 Transaction을 이용하는 통합 지점이다. current/backup의 행 교체와 분리돼도 앱 삭제·전체 DB 복원/리셋에는 증거가 소실되거나 서로 어긋날 수 있다. 새 구매/환생/리셋/백업 복원 전에 저널과 스냅샷을 대조하고 미정산을 조정하는 정책·기술 연결이 남는다.

## 3. 서버 구매 견적과 심사 결과

validateDevelopmentCompositeQuote는 신뢰된 서버 공통 설정과 서버가 신뢰할 수 있는 보유 회차를 입력으로 받아 BigInt로 매 구매 개별 올림·금 증가 회차·두 비용을 재계산한다. 클라이언트 가격/버전/owned를 그대로 승인하지 않는다. 임시 숫자를 서버에 따로 복사하지 않으며 development_balance.json의 서버 배포본을 읽어 전달하는 계약이다. 현재 실제 배포본 생성/서버 구매 엔드포인트에는 미연결이다.

서버가 로컬 스킬 수량을 어떻게 신뢰할지는 기기/진행 권위 결정 전이므로 요청의 owned를 authoritativeOwned로 전달해 우회하지 않는다. 형식 검증은 소유·해금·잔액·동시 구매 검증의 대체물이 아니다. 큰 수 재화는 10진 문자열, 지수·분수·선행0·음수는 거부한다.

recordDevelopmentRewardDecision은 계정/증거 ID/종류/버전/fingerprint와 최종 심사 결과를 같은 문서로 보존한다. 같은 요청은 같은 결과, 다른 내용이나 미당첨→당첨 전환은 충돌이다. 광고는 미당첨(noWin) 추첨을 허용하지 않는다. unverifiable는 최종 검증불가 거절이며 조사 중은 pending으로 유지한다. 실제 추첨·판매 증거 검증·황금/grant 지급은 이 함수가 하지 않는다. 서버 트랜잭션 재실행 중 추첨을 재생성하지 않도록 동일 판매의 고정 판정 근거와 최종 지급을 원자 연결하는 후속 구현이 필요하다.

클라이언트 RewardReviewRecord도 같은 증거의 심사 결과만 기록하고 미당첨을 재시도로 지우지 않는다. eligible/verified는 **자격 확인**이지 지급 완료가 아니며 황금 잔액·구매 가능액을 올리지 않는다. outbox 자동 삭제/이력 정리는 추가하지 않았다.

## 4. 서버 광고 예약과 검증

reserveDevelopmentAd는 Store.run 안에서 기존 시도와 KST 일일 슬롯을 읽고, 한도2 확인·일일 예약·시도 생성을 함께 기록한다. Firestore 트랜잭션의 충돌 재시도가 동시 기기 예약을 직렬화해야 한다. MemoryStore 테스트 소스는 순차 시나리오이며 실제 Firestore 동시성 검증을 대신하지 않는다.

같은 시도 ID는 자정 뒤나 설정 변경 뒤에도 최초 시작일·보상량·버전 그대로 반환한다. 신규 시도만 현재 서버 시각/정책을 사용한다. 예약/검증대기는 계속 슬롯을 점유하며 임시 timeout 숫자만으로 자동 해제하지 않는다. 최종거절만 원래 날짜의 슬롯을 해제하고 이후 성공 콜백을 차단한다. verified도 슬롯을 계속 점유한다.

검증 성공에는 신뢰된 업체 검증 어댑터가 전달한 provider·거래 ID·계정·시도·버전 근거가 필요하다. 업체/거래 ID 쌍의 SHA256 키를 전 계정 공통 보호 문서로 만들어 같은 광고 완료 증거를 다른 시도/계정에 재사용하지 못하게 한다. 증거와 시도 상태는 같은 트랜잭션에 기록하고 모든 읽기를 쓰기 전에 수행한다. 이것은 **증거 귀속/재사용 검사**이며 서명 자체를 검증하는 코드는 아니다. raw SDK callback이나 클라이언트 payload를 VerifiedDevelopmentAdProof로 변환해 신뢰하지 않는다.

아직 선택하지 않은 업체의 SDK·서명/발급자/앱/광고단위/시간 검증, 개인정보/동의, 실제 server grant+지갑 반영, 광고 타이머/세션 복구는 연결하지 않았다. 광고 시청 중 세 타이머 정지 정책은 유지하며 전체 앱 백그라운드 정책으로 확대하지 않는다. 현재 무광고 정책/테스트는 유지한다.
