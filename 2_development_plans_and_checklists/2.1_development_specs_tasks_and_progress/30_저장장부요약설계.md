# 30. 저장 장부 요약 설계 (판매·생산 결과·단골 방문)

작성 2026-11-24 · 브랜치 `dev/stabilization` · 근거 [28번 10절](28_구조개선계획과결과.md) · 상태: **구현 완료(2-A schema 14, 2-B schema 15)**

가게 저장(`WorkshopState`)에는 판매·생산·단골 방문이 생길 때마다 기록이 한 줄씩 쌓이고 지워지지 않는다. 출시 뒤에는 저장 형식을 바꾸기 어려우므로 **출시 전에** "끝난 기록은 요약으로 바꿔 보관"하도록 바꾼다. 표기: **[확인]** 코드에서 확인, **[추천안]** 제안.

## 1. 지금 쌓이는 것 [확인, 측정은 28번 10-1]

| 기록 | 1건 크기 | 쌓이는 때 | 지금 쓰는 곳 |
| --- | --- | --- | --- |
| `sales[<판매ID>]` 판매 증거 | 약 640바이트 | 판매 완료마다 | 불러오기 검증(판매 수 = `completedSales`, 판매 대금 합 ≤ 누적, 재고 묶음별 판매량 ≤ 생산량, 단골 관계 `sale:` 항목 대조), 단골 선택 이벤트 조건 `_choiceFacts`, 태오 사진 반응 `photoReactionSale`, 태오 새 맛 주문(`state.sales` 전체 훑기) |
| `pendingGold['sale:<ID>']` | (schema 13부터 ID만) | 판매 완료마다 | 보상 동기화 `syncRewards` |
| `rewardReceipts['sale:<ID>']` 서버 심사 결과 | 수백 바이트 | 서버 응답마다 | `syncRewards`(끝난 것은 건너뜀) |
| `inventory.dispositions[<결과ID>]` 생산 결과 지문 | 약 120바이트 | 굽기 결과마다 | 같은 결과를 다시 열어 새 제품으로 만드는 것 방지, 판매 검증의 "생산 근거" |
| `relationships.visits[<방문ID>]`·`actions['sale:<ID>']` | 수백 바이트 | 단골 방문·판매마다 | 만난 손님(`met`), 마지막 방문일, 하루 방문 수, 선택 이벤트 조건(방문 수·방문한 날 수·스케치·일·달리기 방문) |
| `purchases.journals` 구매 기록 | 수백 바이트 | 구매마다 | **유료 결제 복구** — 이 설계에서 다루지 않음 |

[확인] 서버는 판매 보상 결과를 판매 ID별로 저장한다(`functions/src/sale_rewards.ts`의 결과 문서·원장 `claimId`). 같은 판매를 다시 청구해도 저장된 결과를 돌려줄 뿐 황금을 두 번 주지 않는다. 그래서 **심사가 끝난 판매를 앱 저장에서 요약으로 바꿔도 결제는 안전하다.**

## 2. "끝난" 판매의 조건 [추천안]

판매 하나를 보관함(요약)으로 옮기려면 **모두** 만족해야 한다.

1. 서버 심사가 끝났다: `rewardReceipts['sale:<ID>']`가 있고 `outcome`이 `pending`이 아님
2. 그 판매가 쓴 재고 묶음이 모두 사라졌다: 판매 증거 `products[].batch`가 `inventory.batches`에 없음(5영업일 소멸 또는 다 팔림)
3. 오늘 영업일의 판매가 아니다(태오 사진 반응은 오늘 판매만 봄)
4. 대기 중인 손님 주문과 관계없다

## 3. 보관함 요약 (schema 14) [추천안]

새 필드 `archive`:

| 값 | 뜻 | 대체하는 계산 |
| --- | --- | --- |
| `sales` | 보관한 판매 수 | 검증 "판매 기록 수 + 보관 수 = `completedSales`" |
| `salesBuns` | 보관한 판매 대금 합(보통 + 특제) | 검증 "판매 대금 합 ≤ 누적" |
| `npc.<손님>` | 단골별 요약: 성공한 판매의 영업일 목록(팥 2개 날·큰 주문 날·일하는 날 구분), 받은 맛 목록, 슈크림 판매 수 | `_choiceFacts`의 판매 부분 |
| `taeoFlavors` | 태오가 받은 맛 목록 | 태오 새 맛 주문의 `state.sales` 훑기 |
| `griddleCycles` | 6구 칸별로 보관한 마지막 회차(`griddle:<실행ID>:<칸>:<회차>`) | 보관한 6구 결과의 `dispositions` |

- 영업일 목록은 날마다 최대 1개씩만 늘어나므로 판매 기록보다 훨씬 작다.
- 보관할 때 판매의 `sales`·`pendingGold`·`rewardReceipts`·관계 `actions['sale:…']` 항목을 지우고, 그 판매만 쓰던 `dispositions`도 지운다(6구 결과는 `griddleCycles`로 재사용 방지, 스페셜 틀 결과는 세션 ID가 무작위라 지운 뒤에는 그 세션 자체가 저장에 없어 다시 열 수 없음 — 구현 때 확인).
- 단골 방문 기록(`relationships.visits`)은 2-2단계로: 방문 수·방문한 날·스케치/일/달리기 방문 수를 손님별 요약으로 옮기고 `met`·마지막 방문일을 요약에서 계산.

## 4. 바꿀 곳

| 순서 | 할 일 | 파일 |
| --- | --- | --- |
| 1 | 요약 필드·보관 함수(순수 함수)와 테스트: 판매 N건을 보관해도 검증 합계·선택 이벤트 사실이 보관 전과 같다 | 새 `lib/workshop_sale_archive.dart`, `test/workshop_sale_archive_test.dart` |
| 2 | `fromJson` 검증을 "장부 + 요약"으로, `_choiceFacts`·태오 주문을 요약 포함 계산으로 | `workshop_controller.dart` |
| 3 | 보관 실행 시점: 새 영업일·보상 동기화 뒤(명령 안에서, 한 번에 최대 N건) | `workshop_controller_daily.dart`, `workshop_controller_commands.dart` |
| 4 | schema 14, 옛 저장(13 이하)은 읽을 때 요약 0에서 시작, 견본·옛 견본 읽기 테스트 | `save_format_test`, 견본 |
| 5 | 2-2단계: 단골 방문 요약 | `workshop_customers.dart` |
| 6 | 측정: Lv.50 시뮬레이션 저장 크기 전후 비교(28번 10-1과 같은 방법) | 28번 문서 |

검증의 핵심 불변식: **보관 전후에 `_choiceFacts`가 돌려주는 사실과 저장 검증 합계가 같아야 한다.** 이것을 1번 테스트로 먼저 고정하고 구현한다.

## 5. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 단골 선택 이벤트 조건이 달라짐 | 보관 전후 `CustomerEventFacts` 동일 테스트(무작위 판매 시뮬레이션 포함) |
| 결제 심사 누락 | 서버 결과가 `pending`이 아닌 판매만 보관. 보관 대상에서 `pendingGold`가 남은 것은 제외 |
| 같은 생산 결과 재사용 | 6구는 칸별 회차 하한, 스페셜 틀은 세션 수명 확인 후 결정. 재사용 시도 거부 테스트 |
| 저장 검증 약화 | 장부에 남은 판매는 지금과 같은 수준으로 검증, 요약은 합계·개수 일치로 검증 |

## 6. 진행 기록

- 1단계(schema 13, 판매 증거 중복 제거): 완료 — 28번 10-2
- 2단계: 설계 완료(이 문서)
- **2-A(무기명 손님 판매 보관) — schema 14, 구현 완료 (2026-11-24)**
  - [확인] 단골 손님 판매는 관계 장부와 촘촘히 묶여 있다: 관계 `actions['sale:<id>']`마다 보상 원장 `awards`가 있어야 하고, 손님별 친밀도는 그 원장 합과 맞춰 검증된다(`workshop_customers.dart` `WorkshopRelationships.fromJson`). 그래서 단골 판매는 2-B로 미루고, 관계·이벤트와 연결이 없는 **무기명 손님 판매만** 먼저 보관한다.
  - 새 순수 함수 `lib/workshop_sale_archive.dart`(`pickSettledAnonymousSales`, `saleBuns`), 상태 `archivedSales`·`archivedSalesBuns`, 명령 안 `_archiveSettledSales`(영업일·심사 결과 수가 바뀐 때만, 저장 성공 뒤에만 확인 표시)
  - 3절의 요약 중 지금 필요한 것은 개수·대금 합뿐(단골 사실·태오 맛·6구 회차는 2-B에서)
  - 생산 결과 기록(`inventory.dispositions`)은 아직 남김(7%) — 2-B와 함께
  - 테스트 `workshop_sale_archive_test`: 보관 후 합계·검증 유지, 심사 전·오늘·단골 판매 남김, 어긋난 합계 거부, 판매 40건 보관 시 저장 크기 비교; `save_format_test` schema 14 견본 + 12·13 견본 읽기
- **2-B(단골 판매 보관 + 다 쓴 생산 결과 지문 정리) — schema 15, 구현 완료 (2026-11-24)**
  - [확인] 단골 방문 기록의 `context.lines`는 그 주문의 줄 목록과 같다(불러오기 검증이 이미 같음을 확인). 그래서 단골 판매의 판매 증거를 지워도 선택 이벤트 조건(팥 주문 날·큰 주문 날·받은 맛·슈크림 횟수·일하는 날)과 태오 새 맛 주문을 **방문 기록에서 다시 읽을 수 있다.** 3절의 손님별 요약 숫자는 만들지 않았다(같은 내용을 두 번 두지 않기).
  - 새 필드 `archivedNamedSales`(보관한 단골 판매 ID 목록, 개수는 `archivedSales`에 포함). 관계 장부(`actions['sale:…']`·보상 원장·친밀도)는 **그대로** 두고, 불러오기 검증은 "판매 기록 또는 보관 목록에 있어야 한다"로 바꿈
  - 방문 기록에 주문 줄이 없는 옛 방문의 판매는 보관하지 않고 남김(`keep`)
  - 생산 결과 지문(`inventory.dispositions`): 재고·준비 제품·장부에 남은 판매·대기 손님의 부분 판매·화면의 결과에 쓰이는 것만 남기고 지움(`keepNeededResults`, `InventoryProgress.retain`). [확인] 결과 ID는 다시 나오지 않는다(제작 세션 ID는 무작위 24자, 6구 칸 회차는 늘기만 함) — 3절의 `griddleCycles`는 필요 없었다
  - 의도한 동작 변경 1건: `workshop_lifecycle_test` "준비 제품 귀속 실패 되돌림"이 "기한 지나 사라진 준비 제품도 지문이 영원히 남는다"를 확인하던 것을 "팔리지 않고 사라진 제품은 지문도 지운다"로 바꿈(재시도해도 나이가 새로 시작하지 않는다는 원래 목적은 그대로 검사)
  - 테스트 `workshop_sale_archive_test` +3개: 단골 3명 판매 보관 전후 선택 이벤트 사실 동일·관계 기록 유지·위조 거부, `pickSettledSales`, `keepNeededResults`; `save_format_test` schema 15 견본 + 12·13·14 견본 읽기
- 단골 방문 기록 요약(3절 2-2단계)은 하지 않음: 방문 기록은 만난 손님·하루 방문 수·선택 이벤트 조건·관계 보상 검증이 모두 쓰는 원본이고, Lv.50 시뮬레이션에서 비중이 1% 미만(28번 10-1 "나머지")이라 바꾸는 위험이 줄어드는 크기보다 크다
- 구매 기록(`purchases.journals`, 16%)은 유료 결제 복구·중복 지급 방지 원본이라 그대로 둠(MASTER_INDEX 4절 구매 보호 코드 유지)
