## 2. 변경된 저장·경제 계약

- Workshop 집계 형식은 **schema2**, SQLite DB 버전은 **2**다. 구형 schema1은 구매 기록이 없었던 형식으로만 읽고 schema2의 purchases 누락은 손상으로 처리한다. `GameState v13` 설정/기존 계정 포트는 바꾸지 않는다.
- SQLite purchase_guard는 current/backup 교체와 구분된 슬롯이다. 현재 집계의 구매 내용과 일치해야 읽고, 지갑/구매 변경과 같은 SQL 트랜잭션에서 저장한다. 명령은 직렬화된 집계 전체를 다시 검증한 뒤 저장한다. guard가 있는데 current가 없거나 서로 불일치하면 자동 초기화·백업 복원을 하지 않는다. **로컬 앱 데이터 삭제/변조를 막는 암호학적 보호는 아니며 서버 진행 증거를 대신하지 않는다.**
- 하나의 로컬 진행에는 미정산 거래1건만 허용한다. 이는 이번 복구 구현의 보수적 직렬화이며 상품 가격/새 보상 정책이 아니다. 다른 계정 지갑으로 원장을 옮기거나 새 ID로 재시도하지 않는다. ordinary offline play는 유지한다.
- 의도 저장부터 미차감 비용을 가용 붕어빵력에서 제외한다. 서버 reserved 뒤 실제 로컬 차감과 debited 근거를 함께 저장한 후 commit을 요청한다. 서버 committed와 차감 근거가 모두 있을 때만 상품을 적용한다. committed인데 차감 근거가 없으면 수동 대조 대상으로 유지한다.
- server reserved는 기존 gold 지갑에서 구매금을 홀드한 상태다. committed는 추가 황금 차감 없이 상품 회차를 확정하고 canceled는 홀드를 정확히1회 복원한다. 불명확한 상태에 TTL/임의 환불을 추가하지 않는다. 지갑의 닉네임 등 다른 필드는 보존한다.
- 적용된 스킬만 공통 설정의 effect를 사용한다. 탭은 기본1+tap 효과 합, 자동은 auto 효과 합이다. 새 계정은 모두0개이므로 실제 초기 자동 생산율0이다. 과거 영수증을 새 가격으로 재계산하거나 현재 가용 황금과 대기 황금을 섞지 않는다.
- 전경은 먼저 기존 자동 생산율로 정산하고 명령을 반영한다. 구매 효과를 구매 전 기간에 소급하지 않는다. 복귀·복구 재읽기는 부재8시간/50% 정산을 먼저 적용한 후 전경으로 돌아간다. 광고 중에는 고객/제작/6구와 탭 입력만 정지하며 경제 시계는 별개다.
- 재고 소비/판매 대금/누적/판매 ID/황금 후보는 여전히 한 번 저장한다. 저장 재시도로 판매된 재고가 되살아나거나 원본 생산량보다 많이 팔리는 저장을 거부한다. 과거 판매 가격을 현재 임시 설정으로 다시 매기지는 않는다.
- 같은 제작 ID·토큰만 맞는 잘못된 입력도 거부한다. 맛·연습 여부·속 순서·기존 반죽을 바꾸지 않은 단일 이벤트로 현재 세션에서 도출 가능한 결과만 허용한다.
- 주문 제작은 활성 손님이 명시한 보유 맛으로 시작한다. 완료 시 익힘 발견·재고를 같은 명령에 저장하며 연습 횟수/손기술은 올리지 않는다. 연습은 완료 후 보관/버리기 선택을 유지한다. 손님 시간이 끝나도 확정 제품을 회수하지 않는다.

## 3. 희귀 판매 황금: 확정 정책과 운영 경계

기존 확정은 ‘오프라인 판매도 서버 검증 후 동일 판매1회 추첨, 검증 불가 시 지급 보장 없음’이다. 기존 공통 임시값 확률1~5%·보상1·하루10 상한을 유지한다. 별5개도 확정 지급이 아니다.

sale_rewards.ts는 신뢰된 SaleRewardVerifier와 서버 시계 함수를 받는다. 날짜는 사용자 확정에 따라 증거 검증 후 각 원자 확정 시도의 서버 시각을 KST로 변환한다. 임의 클라이언트 payload, 로컬 별점/재고/일시, 단순 로그인 여부를 검증 완료로 간주하지 않는다. pending은 추첨/지급하지 않고, unverifiable/noWin은 최종 결과를 보존한다. 당첨 결과·일일 누적·기존 지갑·고정 지급 ID를 한 트랜잭션에 저장한다. 서버 전용 키를 사용하는 고정 HMAC 추첨에는 modulo bias를 피하는 rejection sampling을 사용하며 키를 응답·설정 JSON에 넣지 않는다. 이 키/실제 verifier는 준비되지 않았다.

사용자 확정: **서버 최초 심사 확정일의 KST 날짜 기준, 초과분 이월 없음**. 재시도는 최초 결과/귀속일을 유지하며 자정 전 검증을 시작해 자정 후 확정하면 후자의 날짜를 쓴다. 광고의 서버 승인 시작일 귀속과 구분한다. 판매 지급과 기존 earned_gold.ts는 동일한 earned 지급 ID를 공유하여 두 코어를 거쳐도 중복 지급하지 않는다.
