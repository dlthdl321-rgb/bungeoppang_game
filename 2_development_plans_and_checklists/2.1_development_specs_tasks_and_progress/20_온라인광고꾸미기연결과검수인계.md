## 2. 실제 온라인을 열기 전 필요한 것

index.ts에 소스상 추가한 callable은 workshopProgressClaim/Transfer, workshopPurchaseReserve/Query/Commit/Cancel, workshopRewardSubmit/Query, workshopAdStart/Query다. 전부 기존 Kakao-Firebase 인증 검사를 통과한 UID만 사용한다. body의 account/verified/debited만으로 권한을 부여하지 않는다.

- `WORKSHOP_ONLINE_ENABLED` 기본 비활성이다. 명시적 true와 올바른 서버 전용 `WORKSHOP_SALE_DRAW_KEY_BASE64` 바인딩 없이는 신규 서비스가 열리지 않는다. 키는 환경 설정에 안전하게 관리하며 저장소·채팅·클라이언트·로그에 넣지 않는다. 이번에는 설정/배포하지 않았다.
- `workshopEvidence`는 **신뢰된 서버 검증 파이프라인만 작성**해야 한다. 클라이언트 제출은 별도 `workshopSubmissions`에 저장하며 그것을 승인 증거로 복사하는 엔드포인트는 없다. Firestore 클라이언트 쓰기는 기존 규칙대로 거부한다. source 문자열 하나를 붙였다고 클라이언트 증거를 승인해서는 안 된다.
- 구매 reservation/debit 증거는 계정·진행·epoch·거래·정확 견적 지문·보호 스냅샷 digest·가용/누적 붕어빵력과 일치해야 한다. 꾸미기는 검증된 레벨도 검사한다. 실제 파이프라인은 서명/보호 원장·생산/소비 연쇄·이중 기기·오프라인 근거를 검증해야 한다. 단순 JSON 구조 검사로 대체하지 않는다.
- 진행 이전 증거는 from/to·현재 epoch·검증된 대상 스냅샷/보호 원장 digest·미정산 해소를 포함한다. 실제 이전 시 구매 잠금을 같은 트랜잭션에서 다시 읽는다. 현재 앱은 타 기기의 새 진행을 무조건 덮어쓰거나 자동 백업 복원하지 않는다.
- functions/src/generated/development_balance.json은 단일 공통 설정의 **생성물**이다. 생성 도구가 앱/문서/서버 사본 일치를 검사한다. 직접 편집하지 않는다. TypeScript rootDir/outDir에 맞춰 package main은 lib/src/index.js로 고쳤다. 실행/배포 통과를 뜻하지 않는다.

## 3. 저장·보상 수신

Workshop schema3/SQLite3는 purchases 외에 rewardAccount·rewardReceipts·adAttempts·avatarEquipment·missions·sceneTime을 저장한다. schema1/2는 신규 보호 필드가 없었던 형식으로만 이전한다. 구형 스키마에 신규 보호 필드를 끼워 넣거나 schema3 필드를 누락하면 초기화하지 않고 거부한다. SQL guard는 구매·보상 계정·수신·광고·미션 신청 원장을 함께 대조한다. GameState v13 설정/계정 포트는 별도다.

보상 최초 제출 전에 원래 계정을 로컬에 저장하고 다른 계정으로 옮기지 않는다. 판매 claim은 고정 주문 ID, 승급 claim은 진행 ID+level 키다. 원본·고정 지문·kind·account·progress·claim·최종 outcome/receipt를 대조한다. eligible은 이미 완료된 서버 지급의 수신 기록이며 로컬 gold를 올리는 명령이 아니다. 확정 후 원본을 삭제하지 않아 재설치/응답 유실을 새 보상으로 해석하지 않는다. 서버 지갑 잔액은 따로 인증 재조회한다.

사용자는 “2번으로 하되 손님 판매로 황금붕어빵 획득 가능하니까”라고 답해 **기존 구매·자동 생산 포함 구성 유지**를 선택했다. 일일은 탭50/전경 붕어빵력 생산1000/스킬3개/기본 자동 생산10, 주간은 탭1000/영업한 날짜3/스킬20개/일일 전체 완료3회가 임시 목표다. 공통 mission_targets/mission_gold_rewards만 조정한다. 판매 희귀 황금이 첫 구매 접근 경로이나 확정 획득 시점/첫날 전체 완료는 보장하지 않는다. 광고를 미션 필수 목표로 새로 넣지 않는다.

미션은 KST 자정/월요일·시계 highwater를 사용한다. 전경 탭/자동 생산만 생산 목표에 합산하며 오프라인 정산·일반 판매 대금·승급 대금은 생산 목표에 중복 합산하지 않는다. 스킬 수량은 서버 확정 적용 시1회만 세고 취소/꾸미기는 제외한다. 일일 전체 완료는4개 목표 충족이 필요하고 신청1회만 주간 전체 완료 수를 늘린다. 신청 당시 목표/진행/가격 revision/임시 보상은 보존한다. 기간 경과는 미신청 과거 보상을 새로 열지 않으며 이미 신청한 서버 심사는 원본대로 복구한다.

서버 미션 지급은 진행 ID 외에 계정+목표+기간(승급은 계정+레벨)의 의미 키도 같은 원자 저장에서 잠근다. 기기 이전으로 claim 접두어가 달라져도 같은 미션의 황금을 다시 지급하지 않는다. 전경 경제는 단조 경과시간을 쓰므로 벽시계를 앞으로 돌려 생산량을 만들지 않는다. 부재 정산은 기존8시간/50%다.

## 4. 광고/개인정보 초안과 운영 전 경계

클라이언트 show 완료/중도 닫힘/SDK 실패는 지급 근거가 아니다. 승인 ID를 먼저 저장하고 같은 ID로 서버 상태를 복구한다. SDK가 예외를 내도 gameplay pause를 finally에서 해제한다. 이미 시청했을 수 있는 광고를 복구하면서 자동 재상영하지 않는다. unknown/응답 유실은 무료 지급·취소로 해석하지 않는다.

서버 시작 승인 시 KST 일자와 보상량을 고정한다. 검증·지급이 자정 이후여도 시작일을 유지한다. customData는 계정 ID가 아닌 무작위 opaque token이며 서버 index로 승인에 연결한다. SSV adapter가 실제 signed query/public key/key ID/서명/발급자/광고단위를 확인한 뒤에만 provider 거래를 승인에 연결한다. 동일 provider 거래는 다른 승인에 재사용할 수 없다. SSV와 앱의 지급 재조회는 같은 earned ID를 사용한다.

실제 AdMob SDK는 설치하지 않았으므로 현재 개인정보처리방침에 “SDK 수집 항목 검토 완료”나 “광고 제공 중”이라고 쓰지 않는다. 운영 전 실제 SDK 버전·광고 식별자·IP/기기/진단/광고 상호작용·동의 SDK·국외 처리/보유·미성년자 설정을 공식 자료와 실제 manifest/패키지로 확인해야 한다. 위 항목은 확인 목록이며 확정된 수집 사실 목록이 아니다. 기존 [개인정보 문서](2.1.3_legacy_code_policies_and_online_setup/privacy_policy.md)는 이번에 바꾸지 않았다.

## 6. 정적 확인과 남은 양

추가 테스트24개는 소스 작성만 했다(인증/수신/광고/아바타/배경9, 미션/기간/전경 시간4, 아바타 구매2, 서버 서비스9). 최종 정적 확인은 Dart157/TypeScript29/Kotlin2 구문·상대 import, TypeScript 전체 --noEmit, Python 도구 AST, Markdown 파일 링크, 공통 앱/서버 JSON·생성 문서 일치, 원장 ID/AC/의존성/완료조건/예상 시간 보존, 과거 이력 바이트 보존·정확한 추가14건, render 반복 일치·공백 검사다. 원장은 완료1/검토 중29/차단2/미착수8이며 완료로 승격한 작업은 없다. Node24 호스트에서 실행한 TypeScript --noEmit은 정적 타입 검사이며, 요구 Node22 서버 런타임과 서비스 동작을 검증한 것이 아니다. Dart/Flutter SDK 타입·컴파일 검증은 수행하지 않았다.

현재 5묶음의 **소스 연결과 검수 인계**를 진행했지만 출시 완료가 아니다. 이번 미션 사용자 결정은 반영했다. 남은 조건은 (1) 신뢰된 서버 검증 파이프라인/설정·실제 보호 스냅샷 이전, (2) 실제 AdMob SDK/SSV/동의·운영 설정, (3) 위 실행 검수와 최신 요구·출시 화면 대조다. 체크리스트의 미완료 작업 수와 상태는 tasks.json을 기준으로 보고한다. 시간을 임의 추정하거나 검토 중을 완료율로 환산하지 않는다.
