## 2. DEC-019 — 영업 시작·종료와 날짜 경계

- **확정 범위:** 앱 종료와 영업 종료는 별개. 실제 새 날짜의 영업만 영업일 순번을1 증가시킨다. 현실 날짜 공백만큼 여러 날 증가시키지 않는다.
- **추천:** 국내 Android 첫 출시에는 한국 시각 **00:00** 경계를 사용하되, 신규 날짜 복귀 시 ‘영업 이어가기’를 명시한다. 날짜 경계는 추천이며 오전5시도 확정이 아니다. 영업 중 자정을 넘겨 계속 플레이하면 첫 영업 행동 전에 같은 날짜 전환 절차를 실행한다.
- **대안:** 한국 시각05:00 경계. 심야 플레이의 날짜 분리가 줄지만 기존 일일 초기화와 별도 시각 관리가 필요하다. 시각만 달라지고 아래 중복 방지 규칙은 같다.
- **추천 이유:** 하루 구분을 이해하기 쉽고 국내 운영·검수 부담을 줄인다. 달력 공백으로 재고가 사라지지 않으며 일일 보상·광고 횟수와 영업일을 혼동하지 않는다.

**구현 규칙 추천**

1. 날짜 구간은 선택한 기준 시각부터 다음 기준 시각 직전까지 `[시작, 다음 시작)`이다. UTC로 기록하고 날짜 키만 선택 시간대로 계산한다. 기기 시간대 변경으로 날짜 기준을 바꾸지 않는다.
2. 영업 시작은 기존 미정산 생산을 먼저 마감하고 영업 상태를 저장한 뒤 성공 표시한다. 새 인정 날짜이면 순번+1·기존 재고 노화/소멸·예약 재검증·준비 제품 귀속을 함께 저장한다. 같은 인정 날짜의 재시작은 순번+0이다.
3. 다른 날짜에 복귀해도 **오프라인 정산 자체는 영업일 증가가 아니다**. 이미 열려 있던 영업의 붕어빵력은 정산한다. ‘이어가기’ 전에는 새 제작·수확·납품·손님 생성 입력을 막고 날짜 전환을 안내한다. 전경 복귀 후 붕어빵력은 영업 중 활성 생산으로 처리하여 안내 화면을 오프라인50% 구간으로 반복 정산하지 않는다.
4. 이어가면 새 날짜를 한 번 인정한다. 예: 월요일→화요일→미접속→토요일 실제 영업 순번 차이는2다. 이어가기 대신 종료를 선택하면 기존 영업의 생산만 마감하고 영업 상태를 닫는다. 그 선택만으로 새 영업일을 만들지 않는다.
5. 영업 종료는 명시적 행동이다. 미완료 주문/제작이 있으면 처리 결과를 미리 보여주고 종료를 확인한다. 추천은 주문 예약 해제·새 방문 중단, 미완료 제작은 사용자가 계속 또는 취소를 선택하도록 하며 저장 대기 거래는 먼저 해결한다. 확정 재고·발견·대금은 삭제하지 않는다. 주문 실패 페널티는 DEC-017 담당 결정이며 추가하지 않는다.
6. 인정 날짜보다 과거 날짜가 관측되면 순번을 줄이거나 같은 날짜를 재인정하지 않는다. 최근 인정 날짜로부터 앞으로 진행할 때만 새 날짜를 인정한다. 서버 시각을 사용할 수 있으면 검증하되, 오프라인 기기 시각 조작까지 완전히 방지했다고 주장하지 않는다.

**실패/취소:** 날짜 전환 저장 실패는 이전 순번·재고·예약·세션을 함께 복원하고 같은 전환으로 재시도한다. 성공 전 새날 판매를 받지 않는다. 종료 확인 취소는 영업 상태 변경0이다. 앱 강제 종료로 확인되지 않은 종료를 소급 적용하지 않는다.

**필요 수치:** 기준 시간대·경계·이어가기 방식은 확정 필요 정책이다. 추가 영업 길이 제한은 제안하지 않는다. **선행/전달:** DEC-018 재고, DEC-006 세션, DEC-020 정산. **상태: 추천.**

## 3. DEC-018·019 — 영업 전 제작과 결과 대기의 제작일

- **확정 범위:** 제작 당일0, 실제5영업일 경과 시 제거. 맛/익힘이 같아도 제작 시점이 다르면 나이를 분리한다. 보관 버튼까지 기다렸다고 제작일을 새로 정하면 안 된다.
- **추천:** 큰 틀은 꺼내기 결과 접수 시, 6구는 직접 수확 접수 시 제작 귀속을 고정한다. 결과 저장·보관 재시도로 갱신하지 않는다. 영업을 아직 시작하지 않은 새 날짜의 제작분은 **다음 실제 인정 영업일에 최초1회 귀속하는 준비 제품**으로 표시한다.
- **대안:** 영업 전 제작분을 직전 영업일에 귀속. 저장은 단순하지만 새 영업 준비품이 시작과 동시에 하루 된 제품이 되어 직관성이 낮다. 첫 영업 전 제품의 별도 예외도 필요하다.
- **추천 이유:** 영업 전 연습·준비를 막지 않고, 보관을 미뤄 신선도를 초기화하는 허점을 막는다. 새 재화·창고 상한을 도입하지 않는다.

**규칙:** 같은 인정 날짜에 영업 종료 후 제작하면 이미 인정한 영업일에 귀속한다. 아직 인정하지 않은 새 날짜/최초 영업 전이면 준비 귀속 상태를 생성 시 고정한다. 다음 실제 영업일 인정 시 기존 확정 재고를 먼저 노화하고 준비 제품은 새 순번에0일로 한 번 연결한다. 오랫동안 영업하지 않았어도 실제 영업일이 없으므로 달력 차이로 노화시키지 않는다. 준비 제품은 영업 시작 전 판매할 수 없다. 나이=`현재 인정 순번−제작 귀속 순번`, 나이≥5는 예약 중이어도 제거한다. 소멸로 예약이 깨지면 대체 제품을 안내한다.

결과를 꺼낸 뒤 보관 선택을 다음날까지 미뤄도 최초 귀속 근거를 유지한다. 귀속된 결과의 보관 시점에 이미5영업일이 지났으면 재고로 되살리지 않는다. 발견/연습 기록의 유효성은 보관 여부와 별개다. 미수확6구는 재고가 아니므로 제품의 제작일을 오프라인 경과로 만들어내지 않는다.

**실패:** 제품·귀속 근거·수확/결과 처리 기록을 함께 저장한다. 준비 제품 연결은 재실행해도 다시0일이 되지 않는다. **필요 수치:** 추가 수치 없음, 귀속 정책 승인 필요. **선행:** DEC-004 보관, DEC-011 수확. **상태: 추천.**

## 4. DEC-006 — 비활성·강제 종료·새 프로세스의 세션

- **확정 범위:** 직접 수확만 재고 지급, 주문은 줄·즉석 제작 중에도 개인 대기 소모. 이탈 중 타이머와 미완료 세션의 지속 방식은 미결정이다.
- **추천:** 앱 비활성에서는 제작·주문·6구의 **상호작용 시간만 정지**, 영업 상태와 오프라인 붕어빵력은 유지한다. 같은 프로세스는 일시정지된 상태, 새 프로세스는 마지막 내구 저장 상태를 복원해 명시적으로 재개한다. 강제 종료만으로 주문 재추첨·칼같은 초기화·자동 수확을 하지 않는다.
- **대안:** 같은 프로세스는 정지·복귀, 새 프로세스는 미완료 세션 폐기. 구현은 줄지만 종료 종류에 따라 손해가 다르고 재추첨 악용 가능성이 커진다. 보관/판매 확정 결과와 거래 기록은 이 대안에서도 폐기할 수 없다.
- **추천 이유:** 힐링 게임에서 전화·화면 잠금 때문에 모든 주문을 잃지 않게 한다. 세션 저장 부담은 늘지만 결과와 타이밍의 복구 경로를 통일한다. 자주 이탈해 시간을 멈출 수 있다는 플레이 영향은 직원3과 정책 승인 필요다.

**저장 규칙:** 단계 완료·꺼내기·회차 배정·주문 입장/예약·수확·납품은 고유 행동과 함께 저장한다. 미완료 연속 입력/시간은 체크포인트로 보관한다. 강제 종료 콜백의 실행은 보장할 수 없으므로 ‘종료 때만 저장’으로 설계하지 않는다. 체크포인트 사이 경과 손실의 허용 폭은 검증 후 정할 값이며 현재 정기10초 저장만으로 무손실을 약속하지 않는다. 칸 맛/배율·주문·결과는 재기동으로 다시 추첨하지 않는다.

유효 수확/납품 접수 때 판정·시각·회차를 고정하고 직렬 명령에 넣는다. 저장 지연은 접수된 행동을 실패로 바꾸지 않는다. 저장 오류 시 해당 명령은 고정 상태로 재시도하며 **다른 경제 명령을 막는 복구 화면**을 제공한다. 오류 화면을 정상 게임으로 무제한 이용하는 것은 허용하지 않는다. 다른 손님의 전경 시간은 오류 발생까지의 유효 경과를 저장하고 복구 대기 중 정지한다. 의도적 저장 장애 악용을 완전히 막는 보안 장치로 보지는 않는다.

**실패/입력 취소:** 센서·포인터 취소는 현재 입력만 끊고 확정 단계는 유지한다. 사용자의 실행 취소는 미완료 제품/보상0, 확정 결과의 저장 재시도는 새 제작이 아니다. `GameState` 밖 세션·예약·입력 잠금까지 복원 대상으로 포함해야 한다.

**필요 수치:** 체크포인트 간격은 기술 검증 후 조정값. 이탈/가림 정지 정책은 승인 필요. **선행/전달:** DEC-009·011·015·017, 직원2/3. **상태: 추천.**

## 5. DEC-020 — 영업 중 오프라인 붕어빵력

- **확정 범위:** 대상은 붕어빵력뿐, 영업 전/종료 후 자동 생산0. 영업 중 앱 종료는 생산을 종료하지 않는다. 기존 부재당8시간·50% 유지.
- **추천:** 생산량과 정산 기준 시각을 같은 내구 거래로 확정하며, 생산량이0이어도 기준 시각을 저장한다. 부재 정산 성공 전에 활성 정산을 시작하지 않는다.
- **대안:** 복귀마다 서버에서 정산. 검증력은 커지지만 오프라인 핵심 플레이·기존 로컬 경제의 범위가 바뀌므로 첫 출시의 필수 전환으로 추천하지 않는다.
- **추천 이유:** 기존 정수 경제·시간 분할을 유지하면서 같은 부재 재지급을 막는다. 수확이나 판매를 몰래 자동화하지 않는다.

**규칙:** 부재 시작 A·유효 복귀 B에 대해 경과=max(0,B−A)ms, 인정 길이=min(경과,28,800,000ms). 영업 중인 `[A,A+인정 길이)`에 기존 속도·부스트 유효 구간별50%를 적용한다. 상한 이후 미지급 시간을 다음 복귀로 넘기지 않고 **정산 기준은 B까지** 전진한다. 저장된 속도·정수 나머지·부스트 만료 구간을 사용하며 현재 복귀 속도를 과거 전 구간에 덮어씌우지 않는다. 반올림 손실을 피하도록 기존 정수 계산/나머지를 보존한다.

영업 종료 시각까지 활성 생산을 먼저 정산하고 종료 상태와 기준을 같이 저장한다. 시작 전 구간은 소급 생산하지 않는다. 전경/부재 전환은 겹치지 않는 반열린 구간으로 나눈다. 부재 시작 기록 없이 강제 종료되면 마지막 내구 정산 시각부터 복귀까지를 부재로 처리하는 추천이며, 저장되지 않은 전경 경과의 정확한 복원은 보장하지 않는다.

기기 시간이 뒤로 갔을 때 음수 경과는0, 마지막 인정 시각을 과거로 되돌리지 않는다. 같은 프로세스 활성 경과는 단조 시간을 사용하고 새 프로세스는 저장 UTC 관측을 검증해 새 기준을 만든다. 여러 resume 이벤트는 한 정산만 실행한다. 정산 실패는 생산량·누적 획득량·나머지·기준 시각 모두 미확정 상태로 유지하고 동일 구간 재시도한다. 성공 후 결과 화면 재열기는 추가 지급0이다.

현재 `resume`은 이득이 있을 때 커밋하는 경로이므로 신규 설계에서0생산 정산의 내구 기록을 별도로 검증해야 한다. `save`/커밋/정산/네트워크 적용을 직렬화하고 ‘오래된 순번이 무시됨’을 해당 명령 저장 성공으로 오인하지 않도록 반영 확인이 필요하다.

**필요 수치:** 새 생산 속도·최대 보유량은 정하지 않는다. 직원4의 성장 산식을 입력으로 받는다. **선행:** DEC-019·010. **상태: 추천, 기존8시간/50%는 유지 기준.**

## 6. DEC-010 — 이전·복구·환생

### 기존 사용자 첫 전환

- **확정 범위:** v12 자산·누적량·코인·별·소유권·서버 지갑/상품 ID 보존. 기존 누적 생산이나 튜토리얼로 숙련·새 도감을 만들지 않는다.
- **추천:** 구형 저장의 미정산 부재는 구형 규칙8시간/50%로 **최초 한 번** 마감한 뒤 신규 영업 상태를 ‘시작 전’으로 이전한다. 과거 영업 여부를 추정해 소급 생성하지 않는다. 원본·변환·자산 비교·SQL 저장·재읽기 검증을 완료한 뒤 전환 성공을 표시한다.
- **대안:** 기존 미정산 구간을 보류해 사용자에게 확인. 권리 판단은 보수적이나 시작을 막는 질문과 복구 상태가 늘어난다. 미정산 권리의 조용한 삭제는 추천하지 않는다.
- **추천 이유:** 기존 정산 권리를 보존하고 앞으로의 명시적 영업 규칙과 분리한다. 이전 재시도는 같은 완료 기록으로 생산·기본 레시피를 중복 지급하지 않는다.

기본 지급은 직원1의 최신 기록인 **팥 미디엄 레시피**를 따른다. 아직 미정인 익힘 수집/숙련 단위는 변환에서 자동으로 확정하지 않는다. 미디엄을3단계로 매핑하거나, 전체 팥 익힘 레시피·숙련·6구 자격을 주지 않는다. 해당 결정 전에는 변환 사양을 개발 착수 완료로 표시할 수 없다. 기존 레벨/접근권의 보존과 신규50레벨 환산은 직원4 결정을 받아 적용한다.

**실패:** 변환 도중 원본을 덮어 확정하지 않는다. 손상·알 수 없는 버전/ID·음수 재고·숙련 불일치는 복구 안내하며 임의 삭제/완성 보정을 하지 않는다. **필요 수치:** 다음 저장 버전·출시 맛 수를 여기서 확정하지 않는다. **상태: 추천, 초기 레시피 단위/성장 이전은 다른 결정 대기.**

### 백업·재설치·환생

**추천:** 게임 진척 백업과 되돌리면 안 되는 경제 처리 기록을 구분한다. 구매/판매 황금 처리·서버 영수증·소비 완료·부재 정산 기준의 최신 보호 기록을 확보하고 백업 복구에도 대조한다. 단순 current/backup만으로 모든 이전 경제 행동의 복구를 보장하지 않는다. 서버 황금은 서버를 권위로 재동기화하고 로컬 백업 수치로 서버를 덮어쓰지 않는다.

구매 전 백업으로 돌아가 붕어빵력만 되살아나는 경우를 막으려면 구매 직전/직후 상태와 처리 기록을 일반 순환 백업과 별도로 보호해야 한다. 로컬 파일 전체 소실에는 이 보호도 없어질 수 있다. 기존 서버 영구 권리 복원과 로컬 붕어빵력·재고·숙련 완전 복원은 다르며, 별도 계정 저장 설계 없이 재설치 무손실을 약속하지 않는다. 확인 불가 거래가 있으면 그 경제 명령을 복구 대기로 두고 임의 재차감·무료 지급·음수 잔액으로 해결하지 않는다.

환생의 초기화 대상·보상·레벨 조건은 **직원4 소유**다. 기술 추천은 영업 종료·경제 거래 정리 후 단일 저장으로 실행하는 것이다. 어떤 자산을 초기화하든 중복 방지 기록·서버 구매 권리·정산 시각·이미 인정한 날짜는 환생을 새 사용자로 취급해 재생성하지 않는다. 재고를 보존하는 기획이면 제작 귀속과 영업일 나이도 보존하여 신선도를 초기화하지 않는다. 스킬/속도가 바뀌기 전 구간을 구 속도로 정산한 뒤 새 속도를 적용한다. 확인 취소는 변경0, 실패는 원상 복원·동일 환생 의도로 재시도한다.

**대안:** 서버 계정 전체 진척 저장/복구. 복구 범위는 넓지만 동기화 충돌·운영 부담이 커 기존 범위를 넘는 별도 결정이다. **필요 수치:** 보호 기록 보관 정책은 기술 설계 필요, 환생 수치/초기화 표는 직원4 대기. **상태: 추천 / 환생 기획은 다른 결정 대기.**

## 7. DEC-001·010·021 — 두 재화 구매의 부분 차감 방지

- **확정 범위:** 구매 시점 **현재 붕어빵력 잔액 AND 현재 서버 황금 잔액**을 비용과 비교한다. 누적 획득량을 소비하지 않는다. 가격·연속 구매 산식은 직원4 소유다. 실제 현금 충전은 기존 IAP 검증 경로를 유지한다.
- **추천:** 지속 구매 의도·서버 예약/최종 결과·로컬 차감/지급 기록으로 복구한다. 서버 지갑과 SQLite를 단일 트랜잭션으로 표현하지 않는다. 황금을 쓰는 복합 구매는 첫 출시 온라인 연결에서만 받는 기술 추천이다.
- **대안:** 모든 붕어빵력까지 서버 권위로 이전하면 결합 차감은 단순해지지만 기존 오프라인 경제와 서버 범위를 크게 바꾼다. 첫 출시 필수안으로 확정하지 않는다.
- **추천 이유:** 명칭 변경 때문에 지갑을 다시 만들지 않고 두 비용·권리의 일관성을 다룬다. 기존 황금 단독 구매 후 소유권 동기화만으로 새 붕어빵력 비용까지 처리할 수는 없다.

| 처리 단계 추천 | 내구 상태·중단 시 처리 |
| --- | --- |
| 구매 의도 | 계정·상품·가격 버전·수량·두 비용·동일 재시도 식별을 저장. 두 잔액 검증, 로컬 비용을 다른 구매가 쓰지 못하게 예약. 사용자 확인 취소는 이 단계에서만 해제 |

| 로컬 지급 확정 | 서버 영수증과 결합해 권리/효과를 한 번 적용. 로컬 저장 실패는 차감 완료 기록을 보존한 채 지급 재시도. 성공 후 버튼 재입력·앱 복귀·동기화도 추가 차감/지급0 |
| 확정 실패 보상 처리 | 서버가 최종 실패/취소를 내구 기록한 경우에만 로컬 차감 되돌림을 한 번 저장. 확정 서버 소비가 있으면 임의 로컬 환불 대신 지급 복구 |

예약의 만료 여부와 최종 확정 결과는 서버가 직렬 판정해야 한다. 서버 준비 응답만 받고 로컬 차감하지 못한 경우 최종 지급을 하지 않는다. 로컬 차감 성공 후 예약이 만료됐으면 확정 실패를 조회한 뒤 로컬을 복구한다. 이미 확정된 영수증이 있으면 만료로 처리하지 않는다. 중간 거래가 남아 있으면 환생·백업 교체·동일 비용을 쓰는 구매를 막고 복구 안내한다. 일반 플레이까지 불필요하게 막을지는 공유 상태의 안전성으로 판단한다.

다른 기기에서 얻은 영구 소유권을 다시 붕어빵력 차감하는 근거로 쓰지 않는다. 반대로 **같은 기기의 미완료 복합 구매**라면 해당 의도에 연결된 차감 완료 증거 없이 영수증만 적용하면 부분 무료 구매가 된다. 계정 변경 시 의도와 영수증의 계정을 검증하고 이전 계정 거래를 새 지갑에 적용하지 않는다.

**제약:** 로컬 붕어빵력의 변조 검증까지 서버가 보장하는 구조는 아니다. 예약/결과 조회와 보호 기록은 추가 설계·구현이 필요한 추천이며 현재 서버 기능으로 이미 제공된다고 쓰지 않는다. 내부 함수/필드/패키지명을 고정하지 않는다.

**필요 수치:** 두 비용·가격 버전·수량 상한은 직원4, 예약 유효시간은 기술 검증 후 조정값. **선행:** DEC-010 복구·DEC-025 초기 경로. **상태: 추천 / 가격은 다른 결정 대기.**

## 8. DEC-022·010 — 판매 황금 추첨·검증·오프라인

- **확정 범위:** 유효 판매 완료 시 드문 황금 보상, 별5개 만점이며 높은 만족도일수록 확률 증가. 최고 별점도 확정 당첨이 아니다. 확률·보상량·적용 판매 범위는 직원4 소유다.
- **추천:** 첫 출시의 황금 대상 판매는 온라인 검증 가능한 판매로 제한하고, 연결 불가 판매는 일반 판매/취향 기록만 확정한다. **오프라인 판매의 황금 제외는 사용자 확정이 아니므로 직원1의 선택 필요**다. 사용자가 원하면 아래 대안을 채택한다.
- **대안:** 오프라인 판매도 고정 판매 증거를 저장해 연결 후 서버 검증·추첨·지급. 연결 전 황금을 잔액에 넣지 않는다. 오프라인 증거의 신뢰와 변경된 가격/만족도 규칙 검증 부담이 커진다.
- **추천 이유:** 로컬 주사위 재추첨과 서버 지갑 조작 위험을 줄이고 지급 상태를 명확히 한다. 연결이 없는 플레이의 희귀 보상 기회가 줄어드는 단점은 숨기지 않는다.

**구현 규칙:** 납품 입력 시 고정한 주문·손님·제품 묶음/품질·재고 나이·요구 충족·대기 경과·판정 규칙 버전을 판매 고유 기록과 함께 저장한다. 로컬 재고 소비·주문 완료·일반 대금·관찰·황금 확인 대기를 원자 확정한다. 서버는 판매 자격과 만족도 근거를 검증한 후 직원4의 확률표로 한 번 추첨한다. **미당첨 결과도 저장**하고 같은 판매 조회/재시도에는 같은 결과만 반환한다. 당첨 결과·지급 ID·서버 지갑 증가는 함께 확정한다. 로컬은 서버 결과를 반영할 뿐 황금을 먼저 만들지 않는다.

서버 응답 유실/로컬 저장 실패는 같은 판매 결과 조회로 복구한다. 미완성 주문·예약·부분 준비에는 추첨하지 않는다. 부분 판매 정책을 바꾸면 추첨 단위를 직원3/4와 다시 맞춰 기회 쪼개기를 막는다. 앱 이탈 중 새 판매를 자동 생성하지 않는다. 오프라인 대안을 선택하더라도 ‘부재 중 자동 판매 보상’이 아니라 **플레이 중 실제 완료한 판매의 지연 검증**이다.

온라인이라는 사실만으로 로컬 재고/별점이 신뢰되는 것은 아니다. 서버가 검증할 주문 발급 근거·허용 제작/판매 증거 범위를 정해야 하며, 클라이언트가 보낸 별점만 믿고 지갑을 지급하는 안은 제외한다. 전면 서버 생산 원장까지 필수로 확장하지 않고, 검증 불가 판매의 보류/거절과 사용자 설명을 직원4·기술 담당이 결정한다. 이 검증 경계가 미정이면 황금 판매 보상의 개발 착수 조건은 미충족이다.

**필요 수치:** 확률·보상·별점 세부 단위는 직원4 대기, 여기서0 또는100%로 대체하지 않는다. **선행:** DEC-004·017 판매 성립, DEC-018 귀속, DEC-021 영수증 복구. **상태: 추천 / 보상 규칙은 다른 결정 대기.**

## 9. DEC-008 — 오디오 기본값·활성 소스·재생 수명

- **확정 범위:** 배경/BGM 독립 선택·저장, BGM 위에 선택적 굽기 소리, BGM/굽기/일반 효과음 분리. 오프라인 오디오 재생은 요구가 아니다.
- **추천:** 기존 BGM/SFX 켜짐·볼륨은 유지. 신규 BGM 선택 기본은 ‘자동(배경에 맞춤)’, 굽기 소리는 기본 꺼짐·볼륨50%. **자동/off/50%는 추천 기본값**이며 사용자 확정이 아니다. 사용자가 명시한 BGM은 배경 변경으로 바꾸지 않는다.
- **대안:** 신규 굽기 소리 기본 켜짐. 조리 분위기는 즉시 전달되지만 기존 사용자에게 갑자기 반복음을 추가한다.
- **추천 이유:** 기존 청취 설정을 보존하며 새 소리를 사용자가 선택할 수 있다. 채널3개와 실제 활성 소스 조건만 두어 칸별6개 중첩 재생을 피한다.

**규칙:** 굽기 루프 조건은 `전경 AND 굽기 설정 켜짐 AND 해당 볼륨>0 AND (큰 틀 실제 굽기 OR 보이는 활성6구 굽기)`이다. 여러 칸이 익어도 루프는 최대1개다. 빈 칸·재투입 대기·처리 대기·정지 칸은 소스로 세지 않는다. 직원2의 최종 탄 상태 대기안을 채택하면 그 칸만으로는 루프를 유지하지 않는다. 익힘 단계별 음색 변화·개별 칸 음원은 추가 확정하지 않는다.

BGM·굽기·SFX 볼륨/음소거는 독립 적용한다. 전경 이탈·전화 오디오 중단 시 모든 출력 중단, 복귀는 설정과 현재 소스를 다시 평가한다. 중단된 탭/SFX를 복귀 때 몰아서 재생하지 않는다. 음소거·오디오 오류·블루투스 전환만으로 제작/주문 시간을 멈추지 않는다. 앱 비활성에 따른 시간 정지는 DEC-006 별도 조건이다.

비동기 곡 교체는 최신 선택만 재생되도록 직렬화/무효화하고, 설정 저장 실패 시 이전 선택·재생 상태로 복원한다. 음원 로드 실패는 게임 진행을 막지 않고 무음·재시도 안내로 처리한다. 화면 재진입·빠른 설정 변경에 같은 루프를 중복 생성하지 않고 화면/앱 종료 시 자원을 해제한다.

**필요 수치:** 굽기 기본 볼륨50%는 조정 가능한 기본값 초안. 추가 음원 수·패키지는 정하지 않는다. **선행:** DEC-006·011 활성 상태. **상태: 추천.**

오디오 기본값은 추천 기술 기본값으로 남겨 반드시 물어야 할5개에 추가하지 않는다. 가격·황금 확률·환생·광고 지급량/일일 경계는 직원4/직원1의 결정 묶음에 넘긴다. 기존 하루2회 광고 요구를 폐지하거나 새 SDK·추적·현실 보상을 추가하지 않는다. 광고 일일 원장은 영업일/환생과 분리하고 같은 완료 보상을 한 번 지급해야 한다는 일관성만 전달한다.

## 12. 검증 범위와 남은 제한

**실행한 확인:** 문서와 해당 코드의 정적 대조, 직원1 최신 답변 기록·직원2/3 추천 교차 검토, 기존 DEC 참조 사용. 파일·테스트의 존재는 통과 근거로 쓰지 않았다.

**미실행:** 게임/서버 테스트, 빌드, Android 실기기·센서·오디오 중단 검수, 실제 SQLite 이전/복구, 실제 지갑·IAP·광고 호출. 게임 기능 구현과 실제 사용자 데이터 이전은 하지 않았다.

후속 검증은 기존 [통합검수기준](../09_통합검수기준.md)에 연결할 시나리오만 전달한다. 새 검수 ID를 만들지 않는다: 같은날 재영업/자정 직전·정각/다음날 복귀·미접속 공백, 준비품/보관 지연·나이4/5, 칸 맛/회차 복원·강제 종료·포인터 취소,0생산/8시간 직전·정각·초과·반복 resume·시계 역행, 동시 save/납품/소멸, 서버 확정 직후 종료·응답 유실·예약 만료·구매 전 backup·계정 변경, 미당첨 재시도·지연 황금·최대 별점, 빠른 곡 변경·여러 칸 굽기·전화/복귀를 확인해야 한다.

현재 개발 착수 차단점은 익힘별 레시피/숙련 단위, 시간 정책 승인, 두 재화 복구 계약, 판매 검증 경계, 직원4의 성장·환생·보상 규칙이다. 추천서를 저장한 것은 그 결정의 승인이나 구현/테스트 완료가 아니다.
