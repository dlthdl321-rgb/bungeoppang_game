## 당시 결정 요약

- 사용자 요청: 다른 기기 사용자끼리 겨루는 랭킹. A(구글 리더보드), B(자체 서버), C(오프라인 공유) 중 **A**로 결정했다.
- Google의 v2 게임 SDK를 Kotlin 브리지와 메서드 채널로 직접 연동했다. 리더보드 ID가 없으면 SDK를 빌드에 넣지 않았다.
- 리더보드 3개: 최고 초당 생산(아이템 제외), 누적 생산(64비트 상한 처리), 최고 콤보.
- 제출 시점: 탭마다 보내지 않고 플레이 중 최대 5분 간격, 레벨업·앱 나가기·순위 보기 때 즉시. 저장 파일과 무관.
- UI: 내 기록 화면의 랭킹 카드(준비 중 / 로그인 / 순위 보기). 순위 화면은 구글 기본 화면을 썼다.

## 16단계로 이어진 것

- 점수 변환(`rankingScores`, 64비트 상한), 제출 시점 규칙(`ranking_config.dart`의 5분 간격), `RankingService` 인터페이스는 16단계에서도 그대로 쓴다.
- 리더보드 연동 코드, 리더보드 ID 리소스, 브리지 채널, 내 기록 화면의 랭킹 카드는 16단계에서 지웠다.

## 당시 남았던 위험 (16단계에서 달라진 점)

- 실제 로그인·점수 제출·순위표 화면은 한 번도 실행하지 못했다. 16단계에서 연동 자체를 없앴으므로 더 확인할 필요가 없다.
- 부정 점수: 점수를 기기에서 계산하므로 부풀릴 수 있었다. 16단계부터는 서버(`rankingSubmit`)가 형식·빈도·증가 폭을 확인한다. 완전히 막지는 못한다.
